# Review: geo-report-gen at 711d8f3 (2026-09-29)

This review covers revision `711d8f3` on `main` with a clean working tree. It is a review, not a
change: the only file it adds is this one. All experiments ran on a copy of the repository, its
748 MB cache and `reports/`, placed in a scratch directory. The machine was Windows 11 with
R 4.6.1 and Quarto 1.9.38.

## Assessment

The system does what it was built to do, and its architecture fits the job. It uses plain R
functions, CSV configuration and catalogs, a per-report snapshot and Quarto rendering, with one
command-line entry point. No redesign is warranted.

The statistical core is careful, and every value I reconciled matched an independent
calculation:

| Value | Report | Result |
|---|---|---|
| Union population with its margin of error | `travis-austin` | matched |
| Interpolated union median | `kc-core` | matched |
| Constant-dollar census incomes | `gary-in` | matched |
| City crime rate | `gary-in` | matched the cached FBI data |

The weaknesses are at three seams rather than in the core:

1. **Where generated text meets rendering.** Some published text is wrong or unexplained:
   - A literal `{index_base}` appears in `ct-capitol`.
   - Significance asterisks have no legend in the economic-development reports.
   - A definitional break in the 1970 and 1980 education data is documented but never shown.
   - A map note describes a symbol the map does not use.
2. **Where two editing routes and several settings layers meet.**
   - Edits outside the `:::` fences are silently discarded.
   - A bulk edit can be silently shadowed for the report it came from.
   - A report-level `history_start` does not change most history charts.
3. **In the iteration loop.** Every build recomputes every block: 11–30 s per report, even
   for a one-word prose edit. An unchanged 12-report batch now takes 168 s to compose. The
   README says 37 s, a figure measured when the catalog had 48 operational metrics instead of
   236.

On history, the charts are strong: many subjects reach back to 1970, 1980 or 1790, with
series kept separate. The prose describes only the ACS or post-2010 window, and turning points
are never described.

The first recommended action is Step 1 of the improvement sequence below, a small set of
correctness fixes for published text. It also includes a check that would have caught
`{index_base}`.

## Findings

Confidence: **high** means reproduced or shown in project output; **medium** means supported
by code and partial evidence. The reproduction commands assume the project root. Run them on a
copy wherever they edit files.

### A. Bugs: incorrect, contradictory or unexplained published output

**A1. Unfilled placeholder in a published report, and a warning lost in batch mode (high).**

- **Evidence:** `reports/ct-capitol/report.html` contains the text "relative to its
  {index_base} count". The report's `_snapshot/values.json` has `"index_base": null`, and
  `render.log` contains `gr-placeholders: unknown placeholder {index_base}`. Its `build.json`
  lists `"warnings": []`.
- **Cause:** [R/blocks.R:239](../R/blocks.R#L239) gives `NA` when the area has no data, and
  `NA %||% ""` stays `NA`. [check_placeholders](../R/compose.R#L182) checks only that names
  exist, not that they have values. Batch renders ([R/batch.R:69](../R/batch.R#L69)) write
  stderr to `render.log`, and only single builds scan it ([R/build.R:34](../R/build.R#L34)).
- **Related:** the `pop-growth` prose still says "Each line shows…" when no chart is drawn.
- **Consequence:** a reader sees template syntax, and the flight log's "batch clean" claim was
  not true.
- **Action:** make `check_placeholders` fail on NULL or NA values, have `render_pool` copy
  `gr-placeholders` lines from `render.log` into `build.json`, and use a no-data prose variant.
- **Verify:** `grep "unknown placeholder" reports/*/render.log` finds nothing, and no rendered
  HTML contains `{[a-z_]+}`.

**A2. Significance marks without a legend in `detail = brief` reports (high).**

- **Evidence:** `austin-core` and `kc-core` tables carry `*` and `(±…)` marks. The report text
  never contains "asterisk" (a grep count of 0, against 11 in `gary-in`). The legend lives in
  the `@facts.note` and PLACES `*.note` records. [R/compose.R:328](../R/compose.R#L328) drops
  every `note` field when `detail` is `brief` (the economic-development profile,
  [config/settings.csv:18](../config/settings.csv)).
- **Same mechanism, other losses:** the explanation of census-year dots ("no margins of error,
  not tested") and the FBI county caveats.
- **Consequence:** readers see statistical symbols and dots they cannot interpret.
- **Action:** separate always-shown legends and caveats (for example a `legend` field, or the
  caption) from depth-dependent explanation.
- **Verify:** every report with a `*` in a table also contains the legend sentence.

**A3. A documented definitional break is never shown (high).**

- **Evidence:** the catalog says of `bachelors_plus_share_census`: "Through 1980 the census
  counted years of school … from 1990 it counts degrees". No report contains "years of school".
  The `gary-in` education chart labels the 1970 and 1980 dots "Bachelor's degree or higher".
- **Cause:** `method_note()` adds the `breaks` text only for the primary metric
  ([R/blocks.R:276](../R/blocks.R#L276), [R/blocks.R:501](../R/blocks.R#L501)). The breaks of
  every other plotted series are dropped. Likewise, "Poverty status in the census is for the
  calendar year before the census" never appears.
- **Action:** collect and deduplicate `breaks` from every metric with plotted data.
- **Verify:** `gary-in` education and poverty notes carry both texts, and other blocks' notes
  are unchanged apart from the added breaks.

**A4. The map note contradicts the map (high, minor impact).**

- **Evidence:** [content/text.csv:46](../content/text.csv) `@map.note` says "darker gray:
  unreliable estimate". [render_block_map](../R/maps.R) marks unreliable tracts with a dashed
  outline and keeps their class color. `lake-in` flags 82 of 131 tracts this way.
- **Action:** fix the template to match the renderer.
- **Verify:** read the `lake-in` map and its note together.

**A5. Turning points are never described (high).**

- **Evidence:** "peaked" appears in none of the 8 reports I read.
- **Cause:** the gate `all(mine$moe %in% 0)` ([R/blocks.R:349](../R/blocks.R#L349)) excludes
  administrative and modeled series, whose MOE is `NA`. Lake County's job count peaked in 1979
  at 201,847 (County Business Patterns). Its catalog `uncertainty` is
  `administrative_no_sampling_error`, so the peak should qualify, but it is not reported.
- **Action:** gate on the catalog `uncertainty` field (`census_count`,
  `administrative_no_sampling_error`) and search within one series. The phrase "The count
  peaked" also needs wording for rates.
- **Verify:** the `gary-in` jobs block reports 1979. Survey series still get no peak.

**A6. The LAUS break marker is at the wrong year (medium, minor).**

- **Evidence:** the `ct-capitol` unemployment chart draws "LAUS redesign (break 2009/10)" as a
  line at 2015, because the event's `start_date` is the redesign date.
- **Action:** add a break year to the event, or date the event 2010.

### B. Design problems with concrete consequences

**B1. Text typed outside the fences is silently discarded (high).**

- **Experiment:** I added a paragraph under a heading, outside any `:::` block, then ran
  `gr.R build gary-in`. The paragraph was gone, with no warning.
- **Why:** [harvest_report](../R/authoring.R#L172) reads only fields, then compose overwrites
  the file.
- **Contrast:** the fenced edit in the same run was saved as a `report:gary-in` record.
- **Consequence:** `report.qmd` looks like an ordinary document. The comment at its top warns,
  but loss is silent.
- **Action:** keep a hash of the generated non-field lines. When they differ at harvest, stop
  with "move this text into a text block or a manifest `text` row".

**B2. Bulk import to a broader scope is shadowed for the exporting report (high).**

- **Experiment:** in an export of `gary-in`, I set `edit_scope` to `default` for a field that
  already had a `report:gary-in` record, then ran `text-import`. The import reported success.
  `in-cities-1827000` (also Gary) then showed the new text; `gary-in` kept its old text.
- **Why:** [R/authoring.R:267](../R/authoring.R#L267).
- **Action:** warn when a narrower record will hide the imported one for any report in the
  file.

**B3. The historical window has four layers, and the documented one is overridden (high).**

- **The layers:**
  1. the catalog's `history_start`, a hard floor;
  2. the settings `history_start` (default, profile or report scope);
  3. block-library options in `catalog/blocks.csv`, such as `history_start=1970` on
     `income-trend`;
  4. `acs_releases()`, which also reads the setting
     ([R/providers/census.R:293](../R/providers/census.R#L293)).
- **Where the conflict comes from:** block options override report settings
  ([R/content.R:39](../R/content.R#L39)).
- **Experiment:** I set `report:<id>,history_start,2015`.
  - Unemployment (1990–), permits (2000–) and poverty (1970–) did not change.
  - `tenure-trend`, which uses only the ACS, lost its 2005–2009 and 2010–2014 periods.
- **Consequence:** README's "Change the historical window" ([README.md:169](../README.md#L169))
  is mostly ineffective, and partly effective in a surprising direction.
- **Action:** decide the intended precedence (see open questions). Record each block's effective
  window in `build.json` either way.

**B4. A missing optional credential removes current data from 7 core blocks (high).**

- **Experiment:** I removed `IPUMS_API_KEY` and the NHGIS cache, then built `gary-in`
  (`--offline --no-render`).
- **Result:** `pop-long-history`, `income-trend`, `poverty-trend`, `labor-force`,
  `jobs-long-history`, `education` and `commute-mode` became error blocks. Their ACS values
  were lost as well as the census-year dots.
- **Why:** `compute_block_metric` computes every metric of a block with no per-metric handling
  ([R/blocks.R:171](../R/blocks.R#L171)).
- **Consequence:** a new user, an unregistered IPUMS account, or an IPUMS outage costs the
  report its core income and poverty views.
- **Action:** catch errors per metric, return `unavailable_rows()` with the message, and list
  them in the availability appendix.
- **Verify:** without the key, the ACS lines render and the appendix names the missing census
  years.

**B5. Metric cache reuse after a provider change (high, developer-facing).**

- **Experiment:** on a scratch two-county union, I flipped `combine_moe` in
  `R/providers/small_area.R`. The rebuild reused the cached rows (MOE `NA`, 0 misses). Only
  deleting `cache/metrics/poverty_rate_saipe` produced the new MOEs (1.15).
- **Why:** the metric key includes code only from `metrics.R` and `stats.R`
  ([R/metrics.R:248](../R/metrics.R#L248)). Provider fields such as `combine_moe`, `series`
  and `name`, which shape results, are outside it. README line 81 claims otherwise.
- **Action:** add the provider file's code version to the key.
- **Value of this cache (measured):** a `gary-in` compose takes 29.7 s with the cache and
  36.6 s when all 611 entries must be recomputed and written. The cache is worth keeping.

**B6. Every build recomputes every block; the README benchmark is out of date (high).**

- **Evidence:** see the measurements below.
- **Why it happens:** there is no reuse between "inputs unchanged" and "recompute everything".
  Only a Quarto render is skipped when unchanged.
- **Consequence:** a caption edit through `content/text.csv` costs about 55 s for `gary-in`.
  README lines 212–231 understate warm compose by 4.5×.
- **Action:** see improvement Step 4. Refresh `docs/benchmark.csv` and README after any change.

**B7. Duplicated truths that can drift (medium).**

- Text resolution is implemented three times:
  - [resolve_block_texts](../R/compose.R#L146) for compose;
  - [current_field_text](../R/authoring.R#L82) for harvest and import conflict checks;
  - [metric_text](../R/blocks.R#L77) for labels.
  They agree today, but a drift would produce false conflicts or silent overwrites.
- `stat_type` appears in both `recipes.csv` and `metrics.csv` and differs for 23 of 236
  metrics. For example, the child care price is `value` in the recipe and `median` in the
  documentation. `catalog --check` passes anyway.
- `history_start` and `breaks` sit in the "documentation" table but change output.
- **Action:** use one resolver function for both callers, and add a `catalog --check` rule, or
  drop the documentation copy of `stat_type`.

**B8. Minor.**

- Provenance "retrieved on" dates come from file modification times
  ([R/compose.R:111](../R/compose.R#L111)). Copying or restoring the cache (a `GR_CACHE` team
  drive is supported) changes every report's text and forces a re-render. I saw exactly this
  in my copy. The `.meta.json` retrieval times already exist for downloads.
- `date:` in `report.qmd` is today's date ([R/compose.R:265](../R/compose.R#L265)), so an
  unchanged batch re-renders every report on each new day.
- `cache/metrics` holds 18,027 results, many stale, with no pruning. 19,627 `.lock` files sit
  beside cache entries.
- `census_hist` and `pop_hist_census` (NBER 1900–1990) are no longer used by any block but are
  still selectable and live-verified.
- Internal keys can reach readers: "no published data for county:09110".

### C. Open questions and unresolved hypotheses

1. **Should a report build fully without IPUMS?** This decides whether B4 needs only graceful
   degradation, and whether the keyless `census_hist` path should be kept as a fallback or
   removed.
2. **What is `detail = brief` for?** Hiding explanatory depth, or also caveats? I assume depth
   only (A2).
3. **Should report and profile `history_start` override the block library's windows?**
   Alternatively, library windows could be the default below the report scope (B3).
4. **Is the report date the build date or the data date?** (B8)
5. **Hypothesis, not verified:** Gary's violent-crime text says +131.8% from 2016 to 2025.
   - The values match the cached FBI data: 460 offenses in 2016 for a population of 76,556
     (600.9 per 100,000), and 936 in 2025 for 67,197 (1,392.9).
   - The span crosses the 2021 move from the FBI's older Summary Reporting System (SRS) to its
     incident-based reporting system (NIBRS), and the sentence does not mention it.
   - Check FBI guidance on comparing counts across that transition before trusting the
     direction of the sentence.

**Bottlenecks.**

- **Single-report edits:** compose (about 30 s) exceeds render (about 23 s). Compose cost is
  R-level data wrangling spread across about 50 blocks (about 0.6 s each). File input and output
  are 11%. The one sizeable hotspot is `nhgis_rows` pasting a 266,000-row lookup key on every
  call ([R/providers/nhgis.R:205](../R/providers/nhgis.R#L205)).
- **Batch:** compose is serial, so it dominates when nothing needs rendering.
- **New geography:** mostly sequential Census API calls, one per table, release and state scope.

**Limits of these measurements.**

- One machine and one run of most scenarios. Repeated runs varied by under 1 s.
- I did not re-run a cold build from an empty cache. It would resubmit two IPUMS extracts under
  the user's account. The README's 690 s is from the 48-metric stage.
- The Dayton timing includes live service latency.

## Historical assessment

**What a reader of the default (general) report learns.**

- **Long-run charts** for many subjects:
  - population from 1790 for counties and 1970 for places;
  - jobs from 1970;
  - median income from 1979, poverty, education and labor force from 1970;
  - commuting from 1990, unemployment from 1990;
  - per capita personal income from 1969, relative to the U.S.;
  - house prices from 1990.
- **Honest drawing:** separate series are never joined, gaps stay visible, recessions are
  shaded, and census dots are distinguished from ACS period bars.
- **Context:** a cited event list, labeled by evidence type with a "timing only" disclaimer,
  and notes that a city's boundaries change over time.
- The Gary report makes the city's decline visible in its charts.

**Where useful history is lost or weakened.**

| Gap | Kind | Evidence |
|---|---|---|
| Prose describes only the latest series, the ACS since 2005–2009 or LAUS since 2010 | Implementation choice (PLAN step 3) | Gary: "median household income … not statistically different from 2005–2009". The chart shows about $69,700 in 1979 (2024 dollars) against $38,731 now, a 45% fall that no sentence states. Unemployment is compared with 2010, a recession peak |
| Turning points never described | Bug (A5) | 1979 job peak |
| Places before 1970 | Source route: the NHGIS time series AV0 starts in 1970. Earlier place counts exist only in per-census tables that need name matching | Gary's 1960 peak (178,320) appears only in an event statement; the availability appendix lists "1790 census to 1960 census, not applicable" |
| Homeownership before 2005–2009 | Omission already planned: the NHGIS tenure series B37 is ranked first in `docs/nhgis.md` | `tenure-trend` starts in 2005–2009 |
| Connecticut planning regions before 2020 | Source limit, with a planned workaround (PLAN step 2) | `ct-capitol` population growth has no data |
| Payroll per employee before 1978 | Price-index limit (PLAN step 1) | Chart starts in 1978 |
| EAVS 2020 is fetched but not shown | Presentation choice | The voting table shows only 2024 |

**Comparability issues needing attention.**

- The education definition changes in 1970–1980 (A3), and the 1970 poverty definition. Both
  are documented and neither is shown.
- The LAUS break marker is drawn in the wrong year (A6).
- The crime trend crosses the move to incident-based reporting, NIBRS (C5).

**Handled well.** Legal-area and fixed-boundary history are distinguished, with no crosswalks
or interpolation used. ACS periods do not overlap. The price index handles the prior-year
census incomes, which I verified: $17,235 × 4.0465 = $69,741.

## Improvement sequence

Each step keeps the tested behavior. Use the project's proven fingerprint method: compose every
report and compare `values.json`, `report.qmd` and block digests before and after. Also rerun
`gr.R test` and a batch.

1. **Correct the published text** (small; about a day).
   - Fix A1: fail on NA placeholders, surface batch render warnings, add a no-data prose
     variant.
   - Fix A2 (always-shown legends), A3 (all plotted breaks), A4 (map note), A5 (turning points
     by catalog uncertainty) and A6.
   - Add one compose-level test: every placeholder referenced by any resolved text has a
     non-empty value.
   - **Preserve:** every number. Only the intended text changes.
2. **Make authoring predictable.**
   - B1: detect unfenced changes and stop.
   - B2: warn on shadowed imports.
   - B3: settle history precedence after the user decides, and record effective windows in
     `build.json`.
   - **Preserve:** the three-way conflict rules and existing report-scope records.
3. **Make failures and caching safe.**
   - B4: isolate failures per metric.
   - B5: add the provider version to the metric key.
   - Unify the text resolver (B7).
   - **Verify:** the no-key and flag-flip experiments above give the corrected results.
4. **Shorten the loop, measuring each change.**
   1. Build the NHGIS lookup once (−3.6 s per report, measured).
   2. Only if about 26 s still matters: add a block-result cache so prose, caption, label and
      order edits skip block computation. Text resolution plus writing the `.qmd` take about
      1.5 s today.
      - Its key must cover everything a block reads: row, resolved settings, pieces, vintage,
        catalog rows, `@phrase`/`label.`/`sentence.` records for the report's scopes, theme
        number formats, code versions, and the fingerprints of raw files read. That way
        `--refresh` and source revisions invalidate it.
      - This is the only change here with real complexity.
      - **Verify:** outputs are identical to a fresh compose, and a refreshed source changes
        the dependent blocks.
   3. Refresh the README benchmark.
   4. Optionally, prefetch all ACS jobs of a report in one parallel batch, which helps new
      states.
5. **Put history into the prose.**
   - Add a long-run sentence across series with the source or definition caveat (PLAN step 3).
   - Add tenure for 1970–2000 from NHGIS table B37.
   - Add Connecticut regions summed from towns (PLAN step 2).
   - Show the two EAVS elections.
6. **Tidy up** (low risk).
   - Add the `stat_type` consistency check.
   - Decide on `census_hist` (open question 1).
   - Base retrieval dates on `.meta.json`.
   - Add a cache-prune note or command.

## Keep and leave alone

**Keep.**

- The one CLI entry point, plain functions, CSV configuration, and the provider registry as a
  list of functions.
- Geography built from published pieces, with explicit modes, rejection of overlaps that cannot
  be resolved, and benchmarks labeled with their share of residents.
- The statistical core:
  - the status vocabulary;
  - recomputation from numerators and denominators, and sorted bins for medians;
  - the overlap and part-whole test adjustments;
  - non-overlapping ACS periods;
  - no splicing across series;
  - constant dollars with prior-year handling.
- The snapshot boundary (renders never fetch data) and the render skip.
- Three-way conflict detection.
- Per-block and per-report failure isolation, and the availability appendix.
- Cited events with evidence types.
- Tests on real fixtures.

**Tempting but not justified by the evidence.**

- **A pipeline framework or a local database:** file input and output are 11% of compose.
- **Quarto freeze or the knitr cache:** chunk code is constant, so the cache would reuse stale
  figures unless it is keyed on block data. Render cost is mostly Quarto overhead.
- **Row-filtered ACS decoding:** measured no gain.
- **Merging `metrics.csv` and `recipes.csv`:** a consistency check is enough.
- **Deleting the 13 library blocks no profile uses:** they are a library, but the
  `distribution` block kind is exercised by no sample and should get one.
- **Any change of rendering engine or a web authoring app.**
