# Review of geo-report-gen (2026-09-29)

Revision reviewed: `711d8f3` on `main`, working tree clean. Review only: nothing in the
project was changed except adding this file. All experiments ran in a throwaway copy of the
project and its cache under the session scratchpad; the project's own cache, reports and
content were not touched. Environment: Windows 11 laptop, R 4.6.1, Quarto 1.9.38 (RStudio),
the project's renv library.

## 1. Assessment

The system does what the brief asks, and it does the hard parts well: geography is resolved
into non-overlapping published pieces, statistics follow Census guidance with visible
uncertainty and status codes, history is a default part of every report with sources kept as
separate series and breaks drawn, text is editable inline and in bulk with real conflict
detection, and every value I reconciled against raw cached source files matched exactly.
The code is readable: one entry point, plain functions, CSV tables as the source of truth, and
comments that explain decisions.

The most consequential problems are:

1. **One incorrect output in a shipped sample.** The County Business Patterns adapter turns
   "this geography is not in this year's file" into a published count of zero, so the
   Connecticut planning region's jobs chart shows a flat zero line from 1998 to 2016 and the
   text says the region is "higher than in 1998 (0; change –)". Any county whose FIPS code
   changed is affected (finding F1).
2. **The documented way to change a block's historical window does not work.** A manifest
   row's option cannot override a library block's option, and a profile's or report's
   `history_start` never reaches library blocks that set their own. The early-childhood
   profile's "focus history on the period with child care data" has no effect (F2).
3. **The appendix explains gaps with the wrong reason** in three sample reports: boundary
   changes and unpublished place parts are reported as "the source table is not available in
   this release" (F3).
4. **The edit-to-preview loop has grown to about 54 s per edit and 165 s for an unchanged
   batch**, four to five times the README's numbers, because every build recomposes from
   scratch and a fresh process spends ~25 s loading and normalizing cached tables before any
   report-specific work (F5, F6). The catalog grew from 48 to 236 operational metrics since
   the benchmark was recorded; the README still quotes the old figures.

None of these needs a redesign. F1 to F3 are small, local fixes. F5 and F6 are two
targeted changes to caching that keep the existing invalidation policy.

## 2. Current system

Path from author input to report (one process per `gr.R build`; `batch` composes all reports
in one process, then renders with up to four Quarto processes):

```
config/reports.csv (geography, mode, profile/manifest)
  -> R/geography.R   parse specs; describe members; pieces (non-overlapping published
                     geographies); benchmark policy; entities (study + benchmarks)
  -> profiles/*.csv or config/manifests/*.csv rows -> catalog/blocks.csv (kind, metrics,
                     compare, viz, options) -> catalog/recipes.csv + metrics.csv
  -> R/blocks.R      per block: compute_metric() for each metric x entity x period
       -> R/providers/*.R fetch long data from cache/raw (17 sources), R/metrics.R
          aggregates pieces (sum, share, ratio, interpolated median, published value),
          R/stats.R MOEs and tests, cache/metrics/<metric>/<key>.rds per entity
       -> values (placeholders), fields, sources, unavailable rows
  -> R/compose.R     resolve text (content/text.csv: report > profile > default; field >
                     library block > kind template), check placeholders, write
                     reports/<id>/_snapshot/{report.rds, values.json, theme.scss, qmd_base.json}
                     and reports/<id>/report.qmd
  -> R/build.R       hash(report.qmd, snapshot, drawing code) -> render with Quarto if changed
       -> R/runtime.R draws charts/maps/tables from the snapshot; quarto/gr-placeholders.lua
          fills {placeholders}; build.json records inputs, sources, timings, warnings
  <- R/authoring.R   next build: harvest inline edits from report.qmd (3-way check against
                     qmd_base.json) into content/text.csv; text-export/import for bulk edits
```

Authoritative representations: `content/text.csv` for text (report.qmd is regenerated;
edits are harvested), `catalog/*.csv` for metrics and blocks, `config/*.csv` for reports,
settings and themes, `content/history_events.csv` for cited context. `reports/<id>/` and
`cache/` are disposable and git-ignored.

Scope changes since the brief that matter for this review:

- Operational metrics grew from 48 to 236 across 17 provider sources (PLAN.md, FLIGHT_LOG.md).
  Eleven of those sources were added on 2026-09-28 to 29: CDC PLACES, County Business
  Patterns (all industries), FEMA National Risk Index, USDA Food Environment Atlas, EAC
  voting survey, Census of Governments finance, FBI Crime Data Explorer, and IPUMS NHGIS
  (census years 1790 to 2000; County Business Patterns 1970 to 1997).
- The general profile now has 12 sections and about 50 blocks; a Gary report renders to
  10,000 words and 56 figures. The user has said reports may be long and they edit down.
- PDF via Typst works with a basic layout (documented). HTML is primary.
- `gr.R new` exists; `gr.R preview` wraps `quarto preview`.

## 3. Findings

Confidence: high = reproduced and traced to code; medium = traced to code, consequence
partly inferred; low = hypothesis.

### Bugs

**F1. County Business Patterns: absent geographies become zero jobs.** High.
[R/providers/cbp.R:50](../R/providers/cbp.R:50) sets a missing row before 2017 to 0 with
status ok, and [line 49](../R/providers/cbp.R:49) marks a missing row from 2017 as
"suppressed". The rule is right for a sector missing from an existing county row and wrong
for a county that is not in the file at all. Evidence in the project's own outputs:
`reports/ct-capitol/_snapshot/report.rds`, block `jobs-long-history`, study values 1998 to
2016 are 0 with method "published count", 2017 to 2021 "suppressed" with reason "fewer than 3
establishments or none"; the rendered chart shows a zero line then 457,173 in 2022; the
rendered text says "County Business Patterns counts for Capitol Planning Region run from 1998
(0) to 2023 (473,777) ... That is higher than in 1998 (0; change –)." Affected: the nine
Connecticut planning regions (codes valid from 2022), Oglala Lakota SD (46102, from 2015),
Kusilvak AK (02158), Chugach and Copper River AK (2019), and any future code change; the
same rule zero-fills sector shares for those counties.
Action: zero-fill a sector only when the county's all-industries row (code `00`) exists for
that year and scope; otherwise status unavailable with a reason naming the code change.
Guard `change_values()` so a first value of 0 (or a `fmt_change` result of "–") never yields
"higher than". Verify: ct-capitol jobs history shows 2022 to 2023 only and no zero line; the
Loving County expectations in `tests/testthat/test-metrics.R` still pass; add a fixture case
for a county key absent from a year's file.

**F2. Block options: manifest overrides are ignored; settings never reach library options.**
High. [R/content.R:206](../R/content.R:206) concatenates the library block's options and the
manifest row's options into one string; [R/core.R:209](../R/core.R:209) keeps duplicate
keys; [R/content.R:39](../R/content.R:39) reads `block_options[[k]]`, which returns the first
duplicate, so the library value wins. Reproduced: `history_start=1970; history_start=2000`
resolves to 1970; `unemployment-trend` with a manifest option `history_start=2010` resolves
to 1990; the early-childhood profile (`config/settings.csv:17`, history_start 2000) with the
library `income-trend` option (1970) resolves to 1970, and `reports/austin-tx` shows income
"1980 census to 2020–2024" despite the profile's note. [README.md:169](../README.md:169)
promises all three layers work. No error or warning tells the author the option was dropped.
Action: parse library and manifest options separately and merge with `utils::modifyList()`
(manifest wins). Decide precedence explicitly; my recommendation: default setting < library
block option < profile setting < report setting < manifest row option, which keeps
`pop-long-history` at 1790 under the default 1990 and lets a profile shorten it. Verify: two
expectations in `tests/testthat/test-content.R`; austin-tx income-trend starts where the
profile says.

**F3. Availability appendix misattributes reasons.** High.
[R/blocks.R:103](../R/blocks.R:103) rewrites a piece-level absence ("no published data for
county:09110 (boundary change or table not published)") into "not published for this period
(the source table is not available in this release)" whenever every entity in the block lacks
the value, which is always true for single-entity blocks (compositions and time-only charts).
Rendered evidence: ct-capitol lists 27 such rows for age, race and household types 2005 to
2019, whose cause is the 2022 boundary change that the same table names correctly for the
population rows; travis-austin lists 18 (place-by-county parts and intercensal estimates not
published for parts); gary-in and tx-cities list "New housing units authorized, 2000 to 2006"
although the block's own note says place FIPS codes exist only from 2007.
Action: take "table not published in this release" from the provider (the ACS raw layer
already stores an empty table with a note, [R/providers/census.R:136](../R/providers/census.R:136))
and otherwise keep the piece-level reason. Verify: ct-capitol's ACS rows name the boundary
change.

**F4. Race and Hispanic origin: the change sentence spans the 2020 coding break.** High
(behaviour), medium (remedy). [catalog/blocks.csv:9](../catalog/blocks.csv:9) limits the
block to 2015–2019 and 2020–2024; [R/blocks.R:604](../R/blocks.R:604) picks the largest
significant shift between them; [content/text.csv:281](../content/text.csv:281) warns that
single-race shares fell because of the coding change. Rendered: travis-austin says "The
largest statistically significant shift was in the White alone, not Hispanic group: 49.1% in
2015–2019 and 46.8% in 2020–2024", exactly the artifact the note warns about; gary-in reports
the Hispanic group (defensible). Two earlier periods (2005–2009, 2010–2014) are dropped
although the engine can draw breaks.
Action: suppress the change sentence for a composition when a definitional break recorded in
`content/history_events.csv` for the block's sources falls between the two periods (or limit
it to Hispanic origin), and show all four periods with the break noted. Verify: travis-austin
no longer describes a White-alone shift across 2020.

**F5. An unchanged build still recomposes everything.** High. [R/batch.R:17](../R/batch.R:17)
composes every report before [R/build.R:75](../R/build.R:75) can decide that nothing changed.
Measured: 30.7 s for an unchanged single report and 164 s for an unchanged 12-report batch
that then renders nothing (section 4). build.json already records the input hashes and the
raw files read (`inputs`, `sources`).
Action: before composing, compare the recorded hashes of manifest, settings, text, theme,
catalog, code and `report.qmd` (so inline edits are still harvested) and the size/mtime of
each raw file in `sources`; skip compose and render when all match and no `--refresh` or
`--force` was given. Verify: unchanged batch well under 30 s; a prose edit, a manifest edit,
a `--refresh`, and a replaced raw cache file each still recompose.

**F6. Per-process table loading dominates a warm compose.** High. Profile of a warm compose of
gary-in in a fresh process (39 s with the profiler on, 30.8 s without): 73% of sampled time
is inside `prov$fetch`; ACS normalization on read ([R/providers/census.R:145](../R/providers/census.R:145):
`acs_decode`, `rbind`, `data.frame`) about 10 s; parquet reads 4.9 s; `paste()` 5.1 s, most of
it [R/providers/nhgis.R:205](../R/providers/nhgis.R:205) rebuilding 266,000 keys on every
metric call; metric-cache reads 2.2 s. A second compose in the same process takes 13.8 s
(memo warm), of which `paste()` is still 3.8 s. The batch shares the memo, so its 12 reports
take 165 to 181 s rather than 12 x 31 s.
Action: (a) store each normalized ACS table (release x table x scope) as a derived parquet
keyed by the provider's code version, as `derived_path()` already does for other providers;
(b) build the NHGIS key column once when the extract is read; (c) look for the same pattern
in `fbi_piece_annual()`. Expected effect: fresh-process compose from ~31 s toward the memo-warm
14 s (estimate from the profile, not measured). Preserve: a decoding change must still rebuild
the derived tables (code-version key), and `--refresh` must still re-download.

**F7. The per-entity metric cache costs about what it saves.** Medium.
[R/metrics.R:193](../R/metrics.R:193) keys each entry on a digest of the fetched data, so the
fetch (the expensive part) always happens first; the cache only skips `aggregate_entity()`.
Measured: reading the 840 to 1,260 entries of a report costs ~2.2 s; recomputing and writing
all 611 entries after a code change added 12.8 s (42.2 s vs 29.4 s), mostly file writes.
The layer holds 20,056 cache files plus 19,627 zero-byte lock files (one per entry, never
removed: [R/fetch.R:52](../R/fetch.R:52), [154](../R/fetch.R:154)).
Action: after F6, measure a compose with this layer bypassed; if the difference is a few
seconds, remove it (keep raw and derived layers) or at least stop creating a lock file per
entry. Preserve: `--refresh` semantics; identical values.

**F8. The report date is part of the render inputs, so every report re-renders once a day.**
Medium. [R/compose.R:49](../R/compose.R:49) and [265](../R/compose.R:265) write today's date
into the snapshot and `report.qmd`; [R/build.R:43](../R/build.R:43) hashes both. Cost: about
67 s for the 11 sample reports (4 workers) on the first build of each day, for an unchanged
document. Action: exclude the date from the hashed inputs or let Quarto insert it at render
time. Verify: a rebuild on a new day reports "up to date".

**F9. Wrong reason in the nominal-dollars sentence for relative-index blocks.** Low.
[R/blocks.R:310](../R/blocks.R:310) treats "no dollar year" as "price index unavailable";
`pcpi-trend` uses nominal dollars on purpose (`index=relative`), so its `change_sentence`
reads "because a price index was unavailable" ([content/text.csv:105](../content/text.csv:105)).
Hidden today because `pcpi-trend.prose` does not use `{change_sentence}`; visible to any new
relative block that uses the kind template. Action: a separate phrase for relative views.

**F10. The `viz` column does nothing for metric blocks.** Low. Only compositions read it
([R/charts.R:159](../R/charts.R:159)); `render_block_metric` chooses by `compare`. An author who
sets `viz=dot` on a trend block gets no change and no warning. Action: validate the column
per kind in `validate_manifest()` or honour it.

**F11. Documentation is stale.** Low effort, real consequence (authors plan around it).
[README.md:212](../README.md:212) to 231 report 37 s to compose twelve reports and 86 s for an
unchanged warm batch; today's numbers are 165 to 181 s and 166 s. [README.md:169](../README.md:169)
describes a history-window mechanism that does not work (F2). `docs/benchmark.csv` is from
the 48-metric era.

**F12. Small unused or hypothetical pieces.** Low. `library(tidyr)` in
[R/core.R:6](../R/core.R:6) with no tidyr call anywhere; the `census_hist` provider and
`pop_hist_census` recipe ([R/providers/pep.R:140](../R/providers/pep.R:140), `catalog/recipes.csv:38`)
are no longer used by any block since NHGIS took over the long population chart
([catalog/blocks.csv:33](../catalog/blocks.csv:33)), though `verify` still checks the source;
`module_context$local_file` ([R/blocks.R:795](../R/blocks.R:795)) points at a `data/local`
folder that does not exist. Keep `census_hist` only if it is meant as the keyless fallback
for users without an IPUMS account, and say so in the catalog.

**F13. Repository hygiene.** Low, the user's call. No key file was ever committed and the
`.env` values do not appear in tracked files. The BLS contact email is in the history of
FLIGHT_LOG.md in five commits (removed from the current file in `711d8f3`); the remote is
private.

### Design improvements (not defects)

**D1. Two meanings of `history_start`.** `catalog/metrics.csv` uses it as the first comparable
period (a floor that is never crossed); `config/settings.csv` and block options use it as the
display window. Same name, different semantics, and F2 shows the layering is fragile.
Renaming the catalog column (for example `first_comparable_period`) and documenting the
precedence from F2 would make routine window changes predictable.

**D2. Availability appendix grouping.** Twenty-two consecutive rows in gary-in say that CDC
PLACES publishes nothing for regions, one per measure. Grouping by source, area and reason
would keep the appendix complete and much shorter. Low priority given the user's preference
for complete reports.

**D3. Render cost.** Drawing all 45 figures and tables of the Gary snapshot in plain R takes
8.8 s; a Quarto render of the same report takes 22 to 27 s; a one-chunk document renders in
3.9 s. So roughly 4 s is fixed Quarto start-up and about 9 s is knitr and pandoc work on a
single-file HTML with 56 embedded images. A figure cache would save at most the 8.8 s of
drawing; not embedding resources would cut the pandoc part but changes the deliverable. The larger lever for authors is F5: after a prose edit the
build spends 30 s recomposing before the 23 s render. `gr.R preview` avoids the compose but
re-executes every chunk on each save.

### Open questions (affect a decision)

**Q1. FBI series across the NIBRS transition.** Gary's violent offenses in the FBI data are
460 (2016), 471, 374, 414, no 2020 to 2021, then 499, 617, 905, 936 (2025); the report says
"+131.8%" since 2016 and draws no break, although the block note mentions the 2021 move to
incident-based reporting. Whether the Crime Data Explorer's "summarized" series applies the
SRS hierarchy rule to NIBRS submissions decides whether a definitional-change event
(`content/history_events.csv`, sources `fbi_cde`, 2021) should split the series. Check the FBI's
NIBRS-to-SRS conversion documentation before describing change across 2021.

**Q2. Crime history length.** `fbi_years` is fixed at 2016 to 2025
([R/providers/fbi.R:13](../R/providers/fbi.R:13)). If the API serves earlier years, the block
is shorter than the source allows.

**Q3. House prices start in 1990** ([catalog/blocks.csv](../catalog/blocks.csv), `house-prices`)
though FHFA county indexes start in 1975 for many counties. Deliberate?

**Q4. The three cache misses per warm batch** for austin-core and kc-core in the project's
00:50 batch log did not recur in the copy (0 misses on two runs); they look like one-time
entries after the last provider edit. Not investigated further.

## 5. Historical assessment

What a reader of the Gary report learns without touching configuration: population 175,415
(1970) to 67,289 (2025) with the 1980s collapse visible as census points and the three
estimate vintages as separate lines; median household income about $70,000 in 1979 (2024
dollars) against $38,731 now, with the county, state, region and nation on the same chart;
poverty 15% (1970) to 33%; jobs in Lake County peaking at 201,847 in 1979 and 146,469 by 1986,
SIC and NAICS as separate series with the 1997/1998 break drawn; unemployment since 1990 with
recessions shaded and the LAUS 2009/2010 break drawn; per capita income at 99% of the U.S.
level in 1969 and 80% in 2024; commuting since the 1990 census; eight cited local events
from 1906 to 2026, each labelled by evidence type. Benchmark trajectories are on every trend
chart, and the text states the area's position relative to the widest containing benchmark
at the first and latest period.

Where usable history is lost or shortened:

- Text describes change only within the latest series (ACS 2005–2009 to 2020–2024), so the
  halving of Gary's real median income since 1979 is only in the chart. PLAN.md item 3
  already proposes a long-run sentence.
- Race and Hispanic origin: two periods instead of four, and the change sentence crosses the
  2020 break (F4).
- Connecticut planning regions: no history at all before 2022 for anything keyed by county
  code; the boundary change is explained, but the appendix gives the wrong reason for the ACS
  rows (F3). PLAN.md item 2 (sum towns) is the right direction for counts and shares.
- Constant dollars start in 1978 (R-CPI-U-RS), so 1974 to 1977 payroll is dropped; PLAN.md
  item 1 covers this.
- Crime starts in 2016 (Q2), house prices in 1990 (Q3).
- Union areas lose census-year points for medians (not aggregable; correct) and get no MOE
  (documented).

Comparability handling that is correct and worth keeping: separate series for estimate
vintages, LAUS methods, SIC/NAICS and Connecticut; census-year points drawn without lines and
never tested; prior-year census income deflated to the right year (checked: $17,235 in 1979
x 4.0465 = $69,741); place values labelled as legal-area histories; non-overlapping ACS
periods with the overlap adjustment available; 2020 differential privacy and race coding
notes; SAIPE from 2005 only; the FEMA "not endorsed" statement.

Statistical checks performed (all matched an independent calculation from the raw cached
files): Gary 2020–2024 poverty 33.1% ±2.6 and bachelor's 14.8% ±1.4 from B17001/B15003 with
the handbook proportion MOE; Gary population 68,113; Kansas City union median household
income $82,705 from the summed B19001 bins (member counties' own-bin interpolations within
0.5% to 1.3% of their published medians); Austin place-by-county parts sum to the place total
(979,539) and the Travis + Austin union counts Travis once plus three parts; Gary LAUS 2025
8.5% with the 11-month footnote; Gary 1979 income deflation; FBI Gary agency totals and the
12-month rule. The dependence adjustment in `diff_test()` (Var(A−B) = Var(A)(1−2w) + Var(B))
is algebraically correct for a part of a whole with independent samples; using the population
share as w for household-based rates is an approximation the code comments state.
